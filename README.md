# Умный поиск на сайте — MVP команды №2 (ИИкузница, задача №3)

Поисковый движок по каталогу ПО: понимает опечатки, неверную раскладку, синонимы, сленг и аббревиатуры, ищет без буквального совпадения слов, ранжирует по релевантности с аккуратным бизнес-бустом (популярность, маржа, контекст клиента), распознаёт запросы «нет в каталоге», пишет журнал без персональных данных и строит из него поисковую аналитику. LLM в цепочке поиска нет: ответ — это всегда реальные ID из каталога.

> **Данные.** `data/synthetic/*` — собственные синтетические данные из пакета передачи (30 вымышленных товаров, 36 размеченных запросов). Это **не** материалы организаторов. Цифры качества ниже ничего не говорят о качестве на реальном каталоге. Настоящий набор ожидается 26.11 — как его подключить, описано в разделе [Реальные данные](#подмена-синтетики-реальными-данными-после-2611).

Архитектура на одной странице: [ARCHITECTURE.md](ARCHITECTURE.md).

## Быстрый старт

### Windows (один запуск)
Нужен Python 3.11+ ([python.org](https://www.python.org/downloads/), при установке отметьте «Add python.exe to PATH»).

```bat
run.bat
```
Скрипт создаёт `.venv`, ставит зависимости и запускает сервер. Откройте http://127.0.0.1:8000 (демо) или http://127.0.0.1:8000/docs (Swagger).

Тесты и оценка качества:
```bat
check.bat
```

Вручную (PowerShell):
```powershell
py -3 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m uvicorn app.main:app --port 8000
.venv\Scripts\python -m pytest -q
.venv\Scripts\python scripts\evaluate.py --sweep
```

### Linux / macOS
```sh
./run.sh                       # сервер на :8000
python -m pytest -q            # тесты
python scripts/evaluate.py --sweep
python scripts/bench_scale.py  # нагрузочная оценка latency (1k/10k/50k товаров)
```

> Запуск с нуля проверен в чистом venv на Linux (Python 3.13). На Windows скрипты не запускались — проверьте `run.bat` на машине команды до записи видео.

## Как это работает

Запрос → нормализация (регистр, ё, CamelCase) → исправление **только неизвестных** слов (неверная раскладка, затем RapidFuzz по словарю каталога) → стемминг Snowball RU/EN → поиск словарных фраз (синонимы, сленг, аббревиатуры) → «концепты» с альтернативами → отрицания («без облака» понижает товары с облаком) → составные слова («вирусов» → «антивирус») → **BM25 по полям** (название ×3, вендор ×2, характеристики ×2, категория ×1.5, описание ×1) + точное совпадение ID/названия → **coverage gate** → **relevance gate + бизнес-буст** → top-K с объяснением.

- **Coverage gate.** Товар попадает в выдачу, только если покрывает ≥ 50% IDF-веса слов запроса. Неизвестное каталогу слово весит много, родовые слова («система», «менеджер») — мало. Поэтому «система для управления рестораном» даёт пустую выдачу, и «ресторан» уходит в отчёт о неудовлетворённом спросе, а «менеджер корпоративных паролей» находит хранилище паролей. Порог выбран по dev-развёртке: на 0.40–0.55 всё одинаково хорошо, взята середина.
- **Relevance gate.** Буст получают только товары с релевантностью ≥ 0.75 от лучшего. Они всегда стоят выше остальных, а сдвиг ограничен ±0.1 (бизнес) и ±0.05 (контекст). Нерелевантный товар не может обогнать подходящий, сколько бы маржи у него ни было (тест `test_no_harmful_boost` с подставным товаром: маржа 0.99, популярность 10 млн).
- **Нет поля — нейтрально.** Если в данных нет маржи или популярности, сигнал = 0.5 (нулевой буст), а в ответе стоит `business.missing`. Ничего не выдумывается.
- **Контекст клиента:** фильтр `category`; `segment` — доля поведения товара в сегменте (из событий); `history` — близость к категории/вендору просмотренных товаров. Всё это действует только внутри relevance gate.
- **Журнал** (`logs/searches.jsonl`, отдельно `logs/zero_results.jsonl`, `logs/events.jsonl`): без IP, User-Agent, user_id и истории. E-mail, телефоны и длинные номера вырезаются из поиска и маскируются в журнале, сессия хранится только как солёный хэш.
- **Аналитика строится из журнала** (не из готовой картинки): доля пустых выдач, p50/p95, доля исправлений и синонимов, CTR и «поиск → заказ», уходы после пустой выдачи (proxy: в анонимной сессии за 5 минут не было успешного поиска), топ неудачных запросов, слова неудовлетворённого спроса.

Пример бизнес-буста (запрос `crm`): без буста P009 «Точка CRM Локальная» (релевантность 1.00) стоит выше P008 «Точка CRM» (0.96). С бустом первым становится P008 (популярность 0.96, маржа 0.79 против 0.75 и 0.26). ERP P024 с хорошей маржой (релевантность 0.10) остаётся ниже gate и буста не получает. В демо это видно при включённой галочке «сравнить с/без буста».

## Результаты измерений

`python scripts/evaluate.py --sweep` → `reports/eval_results.md` и `.json` (с разбором по каждому запросу).

**Метрики.** Recall@10, MRR@10 и nDCG@10 (бинарная релевантность) считаются по 32 обычным запросам. Для 4 запросов «нет в каталоге» считается zero detection — доля правильно пустых выдач. Дополнительно: false zero (пустая выдача там, где товар есть) и доля пустых выдач по всем запросам. **Split:** нечётные Q → dev (на них настраивали), чётные → test.

| Шаг (накопительно) | Recall@10 | MRR@10 | nDCG@10 | false zero | zero detect |
|---|---|---|---|---|---|
| A0 BM25 по полям, без морфологии | 0.875 | 0.812 | 0.829 | 0.062 | 0.25 |
| A1 + стемминг RU/EN | 0.969 | 0.885 | 0.907 | 0.031 | 0.25 |
| A2 + словарь синонимов/сленга | 0.969 | 0.938 | 0.946 | 0.031 | 0.25 |
| A3 + лексикон команды (аббревиатуры, RU/EN) | 1.000 | 0.984 | 0.988 | 0 | 0.25 |
| A4 + опечатки/раскладка | 1.000 | 0.984 | 0.988 | 0 | 0.25 |
| A5 + отрицания, родовые слова, покрытие названия | 1.000 | 0.984 | 0.988 | 0 | 0.25 |
| A6 + coverage gate | 0.938 | 0.938 | 0.938 | 0.062 | **1.00** |
| A7 + бизнес-буст с relevance gate (**v1, заморожена до правок по test**) | 0.938 | 0.938 | 0.938 | 0.062 | 1.00 |
| A8 + составные слова (**правка после просмотра test-ошибок**) | 1.000 | 1.000 | 1.000 | 0 | 1.00 |

Все 36 запросов (dev + test). Разбивка по dev/test — в `reports/eval_results.md`. Честное прочтение таблицы:
- **v1 на test:** Recall@10 = MRR@10 = 0.875, false zero 2/16 («защита серверов от вирусов», «вкс для конференций»), zero detect 2/2. На dev — 1.0 везде. Снимок: `reports/eval_v1_frozen_before_test_fix.md`.
- A8 исправляет именно эти две test-ошибки, поэтому финальное 1.0 на test **заражено** и не является оценкой обобщения. Кроме того, test-часть видели при чтении файла.
- Coverage gate — осознанный компромисс: детекция «нет в каталоге» растёт с 0.25 до 1.0, ценой появления false zero, пока не добавлены составные слова.
- Шаги A4 и A5 на этом наборе метрик не меняют: «антивирс для пк» находился и без исправления (через «пк» → «рабочая станция»). Их полезность подтверждают поведенческие тесты (`мониторинк`, `vjybnjhbyu`, `crm без облака`).
- Бизнес-буст на размеченных запросах не меняет top-1 ни разу (аудит в отчёте). Вредных подъёмов (товар ниже gate выше прошедшего gate) — 0.
- **Отвергнутый эксперимент:** «синоним только как запасной путь, если исходное слово не нашлось» снизил MRR@10 с 1.000 до 0.984 («субд для локальной аналитики» уехала на 2-е место) — откатили.

**Latency.** На 30 товарах внутри процесса p50 ≈ 0.08 мс, p95 ≈ 0.11 мс; через HTTP (uvicorn, без кэша) p50 ≈ 2.4 мс, p95 ≈ 3 мс. На размноженном синтетическом каталоге (`reports/bench_scale.md`; оценка пессимистичная, потому что слова очень частые):

| товаров | индексация | память индекса | p50 | p95 |
|---|---|---|---|---|
| 1 000 | 0.3 с | 3 МБ | 0.8 мс | 1.6 мс |
| 10 000 | 1.7 с | 26 МБ | 10 мс | 33 мс |
| 50 000 | 8.7 с | 134 МБ | 73 мс | 383 мс |

## Тесты

`python -m pytest -q` — 56 тестов, все проходят. Запросы в тестах намеренно **не совпадают** с набором оценки.

| Требование ТЗ | Тест |
|---|---|
| точное наименование / ID | `test_exact_name`, `test_exact_id`, `test_partial_name_prefers_fully_covered_name` |
| аббревиатура | `test_abbreviation` (вкс, субд, эдо, iam, wms) |
| синоним | `test_synonym` (видеозвонки, резервная копия, …) |
| опечатка, раскладка | `test_typo` (антивирс, мониторинк, тикетнеца, vjybnjhbyu), `test_typo_does_not_touch_known_words` |
| сленг | `test_slang` (тикетница, срм, бэкап) |
| несколько ограничений | `test_multi_constraint_*` (отрицание «без», on-prem+linux+api), `test_category_context_filter` |
| несуществующий товар | `test_nonexistent` (5 запросов: пусто + слова в отчёте спроса) |
| нет поля маржи | `test_missing_margin`, `test_missing_all_business_fields`, `test_csv_with_other_columns_and_missing_fields` |
| повтор запросов | `test_repeat_deterministic`, `test_repeat_queries` (кэш, оба вызова в журнале) |
| нет ПДн в логах | `test_no_pii_in_logs` (e-mail, телефон, ИНН, сессия, история) |
| нет вредного буста | `test_no_harmful_boost`, `test_gate_invariant_on_all_eval_queries`, `test_boost_only_reorders_close_candidates` |
| аналитика из логов | `test_zero_results_logged_separately_and_in_analytics`, `test_funnel_from_events` |
| морфология RU | `test_morphology` |

Тесты на новых запросах нашли и помогли исправить три реальные ошибки: телефон утекал в журнал через нормализованный текст; «автосервис» ложно совпадал с «сервис-деск»; «crm для продаж» засчитывалось дважды через одну словарную группу.

## Ограничения

- Набор оценки маленький (30 товаров, 36 запросов), его писала та же команда, и он насыщен: финальные 1.0 — не показатель качества. Нужна разметка на реальных запросах.
- Поведенческие события синтетики случайны и не привязаны к запросам. Они используются только для проверки импорта и сегментного контекста и **не** влияют на популярность по умолчанию.
- Бизнес-эффект (конверсия, уходы, потерянные заказы) прототип **не доказывает**: без A/B-теста есть только поисковые proxy-метрики.
- Семантический поиск «по смыслу» сейчас словарный (синонимы, аббревиатуры, составные слова). Эмбеддинги не подключены — их стоит добавлять только при измеримом выигрыше на реальных данных.
- «Связанные запросы» — простые: синонимы найденных концептов и категории топа. Аналоги и сопутствующие товары появятся, когда придут справочники.
- Кэш вкладов терминов и LRU-кэш ответов живут в памяти одного процесса.
- Диалоговое уточнение потребностей не реализовано: организаторы его не подтверждали.

## Инфраструктура и стоимость

- Платные API, LLM и внешние сервисы не используются. Стоимость на синтетике — 0 ₽, ключей в репозитории нет.
- Зависимости: FastAPI, uvicorn, pydantic, RapidFuzz, snowballstemmer (+ pytest, httpx для тестов). Все открытые, ставятся из PyPI.
- Ресурсы: 1 процесс Python. По замерам выше каталогу до ~10 тыс. позиций хватает 1 vCPU и < 0,5 ГБ RAM. Для публичного демо достаточно самой маленькой виртуальной машины (цену уточнить по тарифу выбранного провайдера) или временного туннеля к ноутбуку.
- Если реальный каталог окажется больше ~50 тыс. позиций, ядро BM25 стоит перенести в SQLite FTS5 / Tantivy / OpenSearch, сохранив логику концептов и гейтов.

## Подмена синтетики реальными данными после 26.11

1. Положите файлы в любую папку (JSON-массив, JSONL или CSV) и укажите пути переменными окружения:
   `IK3_CATALOG`, `IK3_SYNONYMS`, `IK3_EVENTS`, `IK3_EVAL`, `IK3_LOG_DIR` (или `IK3_DATA_DIR` для всех сразу; см. `app/config.py`).
   ```bat
   set IK3_CATALOG=D:\real\catalog.csv
   set IK3_SYNONYMS=D:\real\synonyms.json
   run.bat
   ```
2. Сопоставьте колонки в `data/field_mapping.json` (`id`, `name`, `description`, `category`, `vendor`, `attributes`, `popularity`, `margin`, `price`; для событий — `product_id`, `event_type`, `segment`). Характеристики могут быть списком, строкой через запятую/точку с запятой или словарём `{"ОС": "Linux"}`.
3. Проверьте `/health`: сколько товаров загружено, у скольких есть маржа и популярность. Если поля нет, буст по нему нейтрален — это нормальный режим работы.
4. Словарь заказчика: формат `{"термин": ["синоним", ...]}`. Лексикон команды (`data/lexicon_team.json`) подключается дополнительно; отключить можно флагом `use_team_lexicon`.
5. Разметка для оценки: `[{"query_id", "query", "relevant_product_ids": [...]}]`. Пустой список означает «нет в каталоге». Если разметки нет, её стоит собрать из журнала кликов и покупок (без утечки в обучение).
6. Перезапустите `python scripts/evaluate.py --sweep` и заново выберите `coverage_threshold` и `relevance_gate` **на dev-части реальных данных**. Сравните с A0 — baseline сохраняется в каждой таблице.
7. Если в реальных данных есть поиск без результатов, прогоните его через `/search` и проверьте, что `/analytics/zero-results` показывает те же запросы.
